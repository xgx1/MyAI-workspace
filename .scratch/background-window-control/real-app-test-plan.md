# 真实应用验收测试方案（待审核）

被测能力：**通用窗口控制**——AI 在后台对指定窗口发键盘、鼠标、滚轮，并取回该窗口的截图/录像，全程不动人的前台窗口、真实指针、键盘输入目标与剪贴板。

本方案只描述"怎么验"，不改产品设计。执行前需要你逐项批准。

## 3. 环境与隔离（每个用例都相同）

- 被测程序一律跑在**嵌套 niri 实例**（winit 后端、独立 `WAYLAND_DISPLAY`、独立 `NIRI_SOCKET`），**不替换也不重启你正在用的 niri**。
- 每个用例独立进程、独立临时目录；用例结束杀进程、清目录。
- 引擎类允许使用独立 HOME 子目录与独立 profile，禁止读写日常编辑器工程配置。
- 全程不执行：`ego --stop`、删除浏览器 profile 锁、热拷贝活动中的 profile、重启 CUA/niri/DSH 生产进程。

证据目录约定：`.scratch/background-window-control/runs/<日期>/<用例编号>/`，内含 `before.json`（焦点/窗口树快照）、`after.json`、`stdout.log`、`*.png`、`*.mp4`、`result.md`。

## 4. 不干扰性不变量（每个用例必须同时满足）

用例判定"通过"必须**同时**满足下列全部，缺一视为不通过：

1. `focused-window` 的 id 与 `focus_timestamp` 前后逐位相同。
2. 人的真实指针位置前后相同（读取合成器侧指针坐标，不移动它）。
3. 人在 seat0 的关键盘输入目标不变：另一个窗口里键入的内容前后面板一致。
4. 剪贴板前后一致：`wl-paste --list-types` 与文本内容逐字节相同。
5. AI 注入的按键**不触发** niri 自己的快捷键（`bind_fired=no`）。
6. 日常浏览器实例（9222）进程与 CDP 身份前后一致。

## 5. 测试用例

> 每个用例都默认附带 §4 的六条不变量检查。"成功判据"写的是硬指标，不接受"看起来对"。

### TC-01 GTK4 键盘输入（对照组）
- 目的：确认基础设施在真实应用上端到端可用。
- 步骤：起 `zenity --entry`；选为目标窗口；注入 `KEY_A`→`KEY_B`→`KEY_ENTER`；读 stdout。
- 成功判据：stdout 恰为 `ab`；焦点与剪贴板不变。
- 现状：**已通过**（`a` 已复现），本用例作为回归基线保留。

### TC-02 GTK4 鼠标点击（对照组）
- 目的：确认绝对坐标映射在带 client-side 阴影的窗口上正确。
- 步骤：`zenity --question`；点 "Yes" 中心（千分比坐标由截图算）；读退出码。
- 成功判据：退出码 0；重复 10 次 10 次通过。
- 现状：**已通过**（修 geometry 映射后）。

### TC-03 滚轮滚动
- 目的：确认 axis 事件被真实应用接受，且只作用于目标窗口。
- 步骤：GTK4 测试窗（长文本可滚动区）；注入 5 档向下滚动；截图对比滚动前后像素差。
- 成功判据：目标窗口内容偏移且位置单调；人聚焦的对照窗口零滚动；坐标落在目标窗口内。
- 备注：需要先写一个 GTK4 滚动测试窗（约 60 行）。

### TC-04 拖拽（按下–移动–释放）
- 目的：确认多事件序列（press→N×motion→release）在真实应用里成立。
- 步骤：GTK4 测试窗里有一个可拖拽方块；从方块中心拖到目标区；截图 + 应用打印落点。
- 成功判据：应用打印的落点与投递坐标误差 ≤ 2 px；人窗口不受影响；无按键卡在按下态（结束时检查）。

### TC-05 浏览器合成输入（预期失败，产出限制）
- 目的：把"Chromium 不认合成输入"从传闻变成有边界的结论。
- 步骤：嵌套实例里起 Helium/Chrome（独立 profile、独立 CDP 端口）打开测试页；注入点击与按键；页面监听 pointermove/down/up/click/keydown 并写入 `document.title`；用 CDP `/json/list` 读 title。
- 成功判据：**本用例的"通过"= 稳定复现"事件未到达页面"**，并记录 Helium/Chrome 各自的版本、窗口激活状态、是否能到 `wl_pointer` 层。
- 产出：`docs` 里一条明确限制条目（含适用版本）。

### TC-06 浏览器 CDP 通道对照
- 目的：证明"浏览器要达到可用，必须走 CDP"这一结论，而不是含糊带过。
- 步骤：同一页面改用 CDP `Input.dispatchMouseEvent` 与 `Input.dispatchKeyEvent`；同样读 title。
- 成功判据：title 变为 `clicked:1` / `typed:...`，10/10 次；且人的浏览器实例零影响。
- 产出：通道选型结论（合成输入 vs CDP 各自适用面）。

### TC-07 Unity 播放器：键盘
- 目的：引擎类最小可用性。
- 步骤：用 Unity 6000.7.0b5 构建一个空场景 + 一个脚本把按键写进 `Application.persistentDataPath` 下的日志；选为目标窗口；注入 W/A/S/D 与空格；读日志。
- 成功判据：日志里按序出现 4 个键 + 空格；帧率不低于基线 80%；焦点不变。
- 备注：需要你确认可用哪个 Unity 版本与许可证状态。

### TC-08 Unity 播放器：鼠标与相对运动
- 目的：验证相对鼠标（FPS 视角）这条最容易被忽略的路径。
- 步骤：播放器里摄像机按鼠标相对位移旋转；注入分多次的相对移动；读旋转角度。
- 成功判据：角度增量与注入量成线性（误差 ≤ 5%）；人窗口零事件。
- 备注：若相对运动路径未实现，本用例转为"记录缺口"，不算通过。

### TC-09 Unreal：窗口启动与键盘
- 目的：UE5 在嵌套合成器里能否正常跑起来，以及按键能否送达。
- 步骤：起一个 UE 工程（打包版优先，编辑器次之）；选为目标窗口；注入按键与一次点击；读 UE 日志（`LogInput` 或自写 Actor 日志）。
- 成功判据：按键次数与内容一致；窗口不崩；帧率 ≥ 基线 70%。
- 风险：UE 需要 Vulkan/GL，嵌套 winit 后端可能起不来（见 §6 R2）。

### TC-10 Unreal：指针锁定 / 相对鼠标
- 目的：同样的相对运动验证，UE 侧。
- 步骤：场景里开指针锁定（`SetInputMode` 仅游戏）；注入相对运动；读旋转。
- 成功判据：旋转量线性；退出锁定后人的指针位置不变。

### TC-11 .NET GUI：键盘与点击
- 目的：覆盖 .NET 交付形态。
- 步骤：Avalonia 测试程序（一个输入框 + 一个按钮，按钮把文本框内容写到 stdout）；注入文本与点击；读 stdout。
- 成功判据：stdout 内容与注入一致；10/10 次。
- 备注：若本机无 Avalonia 模板/离线包，改用 GTK4 + .NET（Gir.Core）；再不行则用 GTK4 原生程序并在报告里标注"未覆盖 .NET"。

### TC-12 截图正确性
- 目的：截图是"看窗口"的唯一手段，必须证明它真、准、无副作用。
- 步骤：对同一窗口分别取（a）我们的 `ScopedScreenshot`、（b）应用自身渲染（浏览器用 CDP `Page.captureScreenshot`，引擎用引擎内截图）；比对尺寸与内容；同时在另一窗口复制一段文本后复验剪贴板。
- 成功判据：内容差异只允许出现在光标/动画像素上（结构相似度 ≥ 0.98）；剪贴板字节不变；截图耗时记录在案。

### TC-13 视频录制
- 目的：验收"录像"能力。
- 前置：需要实现 `ScopedScreencast`（见 §7）。
- 步骤：录制目标窗口 10 秒（≥15 fps）；同时让窗口内容持续变化（引擎里让物体动、浏览器里跑动画）；用 `ffprobe` 验时长/帧数；抽 3 帧与实拍帧比对。
- 成功判据：时长 10±0.5 s；帧数 ≥ 150；抽帧内容与对应时间点一致；人的前台全程不受影响；CPU 峰值记录在案。

### TC-14 非干扰性并发（人的输入 vs AI 的输入）
- 目的：这是整个功能的立身之本，必须独立成用例。
- 步骤：两个窗口，A 为 AI 目标、B 为人聚焦窗口；在 5 秒内：人向 B 持续键入，AI 向 A 持续键入并点击；各自记录收到的键序列。
- 成功判据：两边序列各自完整且互不包含对方按键；焦点 id 与 `focus_timestamp` 不变；AI 按键不触发快捷键。

### TC-15 目标切换与失效
- 目的：真实使用中目标会变、窗口会关。
- 步骤：（a）运行中把目标从 A 切到 B，再切回；（b）目标窗口中途被关闭；（c）把目标指向 X11 窗口。
- 成功判据：（a）切换后事件只到新目标，旧目标立即收不到；（b）关闭后不崩、不把输入送给别的窗口（当前焦点窗口零事件）；（c）X11 目标被明确拒绝且不误投递。

### TC-16 缩放与 HiDPI
- 目的：不同 `scale` 下点击仍要落在同一物理位置。
- 步骤：同一应用分别在 scale 1.0 / 1.25 / 1.5 下运行；点击同一相对位置；对比落点。
- 成功判据：落点相对误差 ≤ 1 px（逻辑像素）；截图尺寸随 scale 正确变化。

### TC-17 长时稳定性
- 目的：排除"跑几分钟就漏"。
- 步骤：对目标窗口循环"点击 + 键入 + 截图"200 次，约 10 分钟。
- 成功判据：成功率 100%；进程 RSS 增长 < 50 MB；无按键卡住；焦点零漂移；结束后清理干净。

## 6. 风险与受限项（必须先摆到桌面上）

- **R1 Chromium 不认合成输入**（已观测，两条通道都试过：agent 座席与真人座席）。若 TC-05/TC-06 确认无法从合成器侧满足，浏览器一律走 CDP，测试方案里"浏览器"的键盘鼠标项改为 CDP 验收。
- **R2 引擎在嵌套合成器里可能起不来**：UE 需要 Vulkan/GL 上下文，嵌套 winit 输出可能不满足。若 TC-09 起不来，需要你决策：是否允许为引擎测试单独启动一个**打补丁的 niri 会话**（会占用显示输出，风险高于嵌套）。
- **R3 Unity 许可证与首次导入**：编辑器启动需要许可证、首次导入耗时 10–30 分钟，且可能弹窗要求交互。若不满足，本方案降级为"播放器（已构建包）测试"。
- **R4 相对鼠标尚未实现**：TC-08/TC-10 目前会暴露为缺口，不算通过。
- **R5 `.NET GUI` 样本需要现造**：无模板/无离线包时降级为 GTK4+.NET 或 GTK4 原生，并在报告中标注未覆盖 .NET。
- **R6 IME/中文输入**未纳入本方案（需要输入法协议通道，另行评估）。

## 7. 视频能力缺口的技术选项（需要你选一个）

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| V1 帧循环 + ffmpeg（推荐） | niri 内加 `ScopedScreencast { window, path, fps, seconds }`，按 fps 反复渲染该窗口到内存帧，结束后管道送 ffmpeg 编码 mp4 | 小，复用已有截图路径 | 帧率上限受渲染循环限制，15–30 fps 现实 |
| V2 走 screencast 协议 | 用 `wlr-screencopy`/`xdg-desktop-portal ScreenCast` 捕获区域 | 中，需要处理 portal 授权弹窗 | portal 授权会弹窗，可能干扰人 |
| V3 外部录屏 | `grim` 轮询 + ffmpeg | 小 | 只能录整屏区域，且会录到人的窗口，**不符合"只看目标窗口"** |
