# 提问不再阻塞：问题落成 Markdown，先用临时方案继续，答复后按答复重做

2026-11-03，用户确认管理会话与工作对话都**不该有会卡住的询问能力**。提问必须变成非阻塞的：问题写进一份提问 Markdown，会话当场用一个临时方案继续推进；这份 Markdown 被答复之后，再按答复重做受影响的部分。

## 背景

现行实现（`session-manager`）里，工作对话调用提问工具后：问题入账、转给管理端、**当前轮次以 `pending` 收尾**，而且该对话的 pre-step 在问题未答期间**拒绝一切后续工作**。管理会话自己的提问走原生定时等待，也会把前台挂住。

这套语义在桌面对话里成立，在本工作流里不成立：用户经常不在旁边，一条提问就能让整条工作线停几个小时，而他真正想要的是"先干起来，回头再说"。

## 决定

- **提问是非阻塞工具调用**：返回"已登记 + 我按临时方案先做"，不结束当前轮次，不进入等待。
- **问题落成 Markdown**：每个管理关系一份提问文档，逐条追加"问题 / 我临时怎么做的 / 当前状态"；答复写回同一份文档，形成可追溯的问答记录。
- **临时方案必须写下来**：继续推进时采用的假设进文档，答复到达后据此判断哪些部分需要重做。
- **答复到达 → 重做**：答复作为一条普通消息投给原工作对话，说明"第几条已答复，按此重做受影响部分"，由它自己决定重做范围；不是把整轮重跑一遍。
- **管理端同样不阻塞**：管理会话收到工作对话的提问时，不再用会挂住前台的原生等待；它要么按已有依据直接答，要么把问题留在文档里继续做别的。

## 影响

- 功能文档里「等待回复」一节作废：不再有"相关工作暂停"这种状态；卡片状态回到「进行中 / 已完成 / 发生问题 / 已暂停」，另有未答问题的数量提示。
- `session-manager` 需要改两处硬逻辑：提问工具不再 `concludeTurn`；pre-step 不再因待答问题拒绝后续工作。
- 回复框的含义从"解开阻塞"变成"把答复写回提问文档并触发重做"。
