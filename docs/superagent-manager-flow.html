任务台 v2 · 两层管理器

一个和 Super Agent 同级的任务台入口，把「我说一段话 → 任务被派下去 → 卡住时回来找我」这条链路做完整。 下面的图是方案，不是已实现的现状 —— 现在只有面板壳、任务记录和 Super Agent 的触发器，管理器那两层还没建。

02结构：两个管理器 + 一个面板

管理器不干活，只调度；干活的永远是执行会话。

你 只在三处出现：派任务 / 答问题 / 拍下一步

其余时间系统自己跑，注意力闸门决定什么时候叫你。

↓ 一段文本（粘贴 job 描述也行）

大管理器 全局一个，常驻

听懂你要什么 → 决定这事属于哪个项目 → 找/建那个项目的项目管理器 → 跨项目的取舍也归它（方向、优先级、要不要拆）。它不直接碰代码。

↓ 项目内派单（带任务文本 + 绑定哪几个触发器）

项目管理器 每个项目一个

建执行会话、盯进度、裁决"下一步"、巡查本项目所有触发器是否健康。会休眠，有活才醒。

执行会话 每张单一个

复用 subagent：独立会话 + 独立 worktree（sa/<ticket> 分支），只干这一件事，不直接对外说话。

触发器 属于项目

inbox / github issue / CI 失败 / 以后 IM、邮件。任务绑哪些源，就算哪些源的事件。项目管理器定时体检它们的连通与配额。

↓ 结果、问题、下一步 都回流到这张任务卡片

任务台面板 与 Super Agent 同一层级的入口

筛选列：我的任务（等我动手）· 问题 · 下一步 · 运行中 · 全部。问题逐条在卡片上答，答完由项目管理器转给对应执行会话。

三条硬边界（防止做成一锅粥）：

管理器只读不写代码

管理模式的工具面里没有文件写入、没有 shell 副作用，避免它和 Worker 抢同一个仓库。

问题不阻塞

提问落成一条待答项，执行会话当场用临时方案继续；你答复之后，受影响的部分按答复重做（ADR-0012）。

管理器不直接问你

它的提问工具变成占位，只回"问题在任务卡片上"（ADR-0013），免得同一个问题问两遍。

03一次任务的经过

点任意一行看它落在谁身上；颜色 = 谁来负责这一步。

  1. 你把一段文本丢进任务台「指派任务」，可顺手指定项目（不指定就让系统判断）。
  2. 大管理器判断项目归属；该项目还没有项目管理器就创建一个（ADR-0010：创建权只在管理端）。
  3. 项目管理器把这段文本拆成一张任务卡片：目标、验收、绑定哪些触发器、预算上限、交付方式（默认 patch）。
  4. 项目管理器起一个执行会话（subagent + 独立 worktree），把任务简报和工具面裁好交给它。
  5. 执行会话干活；过程中产生的"我要继续做 X"和"这里有个问题"都记到任务卡片上，同时用临时方案继续跑。
  6. 触发器期间到达的相关事件（CI 挂了、issue 有人回）直接进这个执行会话的线程，不再重复过一遍准入。
  7. 项目管理器裁决每个回流项：能自己定的就回「继续，按你推荐且保险的方式做」，并把理由写进卡片；定不了的才升级到你那。
  8. 你在任务台的「问题 / 下一步」筛选列里逐条处理，一次一条，不打断别的事。
  9. 执行会话按你的答复重做受影响的部分，交付 patch（或 push / PR），把回执回贴来源线程。
  10. 项目管理器关单；同时按周期巡查：本项目所有触发器是否还活着、配额是否见底、有没有反复失败的单。

第 7 步是这套设计的关键："推荐且保险"不是一句口号，得是规则 —— 例如只允许 patch 交付、不碰受保护分支、不改别人的仓库配置、预算用完就停手。规则的默认集我们 v0.1 先定死，不给项目管理器自由发挥。

05你做什么 / 它做什么

你
  • 贴一段文本派任务（可指定项目）
  • 逐条答任务卡片上的问题
  • 需要时覆写项目管理器给的"下一步"
项目管理器
  • 拆单、绑触发器、定预算
  • 起执行会话、裁工具面
  • 裁决回流项：继续 / 升级给你
  • 巡查本项目的触发器与失败单
执行会话
  • 在独立 worktree 里干活
  • 问题与下一步都回报，不等答复
  • 交付 patch / push / PR，回贴来源

注意力预算：一个项目同时最多 1 条"需要你"的提醒；同一张单没新进展就静默。你不在线时整条线继续跑，不因提问停摆。

06复用什么 / 新建什么

能力性质落点

07待你拍板（拍完我就照这个做）

这几条不定，做出来就会返工。绿色是我的建议。

"项目"用什么定义？

决定项目管理器的边界和触发器归属。三种候选：DSH 工作区记录、git 仓库根路径、你手写的项目清单。

建议：git 仓库根路径为主键，工作区只是它的一个视图入口。

项目管理器是常驻会话，还是按需创建 + 休眠？

常驻 = 一直在上下文里，成本高但反应快；按需 = 省钱但要冷启动。

建议：按需创建，空闲 30 分钟休眠，唤醒走"项目内有新事件"。

任务事实源放哪？

ADR-0011 说清单是纳管会话的视图；Super Agent 却自带工单库（storages/super-agent）。两套并存就会出现"同一个单两个状态"。

建议：一张单只有一个 owner —— 交给 Super Agent 的工单库，面板做视图；ADR-0011 的那条修订为新 ADR。

触发器归属：属于任务还是属于项目？

你说"任务会关联相关触发器"，但巡查和配额又天然按项目算。

建议：配置挂项目（谁读谁的凭据、配额按项目算），任务只声明"我要订阅哪几个"。

"推荐且保险的方式"的边界谁来定？

如果让项目管理器自己判断，它迟早会决定 push 代码或改别人的仓库。

建议：v0.1 硬编码一份允许清单（只 patch、不 push/PR、不碰受保护分支、不跨仓库），要放宽得改配置并留痕。

大管理器 v0.1 必须存在吗？

它的作用是判断项目归属和跨项目取舍；如果一开始只有一个项目，它几乎没活干。

建议：v0.1 先用一条"文本 → 项目"的规则代替它，等真有两个项目在建了再接大管理器，避免一上来就要处理它的上下文成本。

08v0.1 切法（只做能立刻手测的那层）

做
  • 入口挪到图标行，整区面板
  • 「指派任务」建单 → 建一个项目管理器会话
  • 项目管理器拆单 + 起执行会话（复用 Super Agent 的 worktree/交付）
  • 问题与下一步落到卡片，两列筛选 + 逐条答复
不做
  • 大管理器（先用规则代替，见 Q6）
  • 触发器巡查的自动修复（先只报健康状态）
  • push / PR 交付（保持 patch）
  • 跨项目调度、优先级、预算仲裁
验收（一条就够）

在任务台贴一段文本 → 出现一张卡片 → 项目管理器起了执行会话并改了代码 → 卡片上出现 1 条问题 → 你答完 → 交付 patch，全程不用开别的页面。
